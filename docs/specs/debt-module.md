# Spec: Debt module

This project uses no issue tracker, so this file is the checklist. Its `status` frontmatter takes the place of a tracker's triage label. Update the status, for example to `in-progress` or `done`, as work goes on.

## Problem statement

Before this module, `Debt` was only a placeholder in `CONTEXT.md`, with no schema, module or UI. There was no way to track money owed to or by another person. A Bank Account's Balance can never go negative, because it models liquid assets only, so credit, liabilities and IOUs had nowhere to live.

## Solution

A `Debt` module tracks money owed in either direction, `receivable` or `payable`. How it touches a Bank Account depends on the direction:

- Creating a `receivable` can be a real movement of money. If the user picks a source Bank Account, the money leaves it right away. The source is optional, so a receivable can also exist with no Bank Account.
- Creating a `payable` is always only a record. No Bank Account is involved until repayment.

Repayments follow the same optional pattern in both directions, and a Debt can have many partial repayments over time. If the user picks a Bank Account, the repayment also becomes a real `Transaction` row. If they leave it empty, the repayment is only a record against the Debt. Either way, a dedicated `debtPayments` table links the repayment to its Debt, so `transactions` doesn't need to know about Debts. The user can also forgive a Debt, which writes off everything still outstanding, all at once and reversibly.

A grilling and domain-modeling session produced this spec. It was then partly built and refined. These parts are implemented: creating a Debt (stories 1 to 3), logging repayments (stories 4 to 9), viewing a Debt (story 10), editing a Debt (stories 11 to 14), editing a repayment (story 15), deleting a Debt (stories 16 to 18), forgiving a Debt (stories 19 to 23), and how Bank Account deletion affects Debts (stories 24 to 26). The ownership audit (story 27) is still only designed. Further notes records what changed between the original session and what shipped.

## User stories

### Logging a Debt

1. As a user, I want to log a new Debt where someone owes me money (`receivable`), giving an amount, a currency, a free-text counterparty name, and optionally one source Bank Account. If I pick one, the money leaving that account to fund the loan becomes a real Transaction. If I don't, the Debt is still recorded, such as for cash lent or money that moved outside this app.
2. As a user, I want the Bank Account picker for a `receivable` Debt to only show accounts in the currency I picked for the Debt, and only accounts with unallocated balance available. Then I can't fund it by accident from an account in the wrong currency or with everything committed, since this app never converts currencies.
3. As a user, I want to log a new Debt where I owe someone money (`payable`), with only an amount, currency, and counterparty name and no Bank Account, so I can record an obligation that didn't start with money this app tracks, such as a cash loan, an older debt, or a promise.

### Repaying a Debt

4. As a user, I want to log a repayment against any Debt, in either direction, giving an amount, date, optional note, and optionally a Bank Account. If I pick one, the money becomes a real Transaction tied back to that Debt. If I don't, the repayment still reduces what's outstanding, such as for cash repaid or money that moved outside this app, for the same reason a `payable` starts without a Bank Account (story 3).
5. As a user, I want the Bank Account picker for a repayment to only show accounts in the Debt's currency, for the same reason as story 2.
6. As a user, I want to repay from any Bank Account in the matching currency, not only the account a `receivable` was funded from, because real repayments vary, such as a loan made from Checking and repaid into Savings.
7. As a user, I want to log several partial repayments against one Debt over time, so I can track it being paid down gradually instead of all at once.
8. As a user, I want a Debt's outstanding amount computed live as its original amount minus everything repaid, so the number can never go stale.
9. As a user, I want to log a repayment larger than what's outstanding, so an overpayment, accidental or deliberate, isn't blocked. The app shouldn't assume it's always a mistake.

### Viewing and editing

10. As a user, I want a Debt's detail page to show its counterparty name, direction, amount, live outstanding, currency, date, and note, with every repayment logged against it, so I see everything in one place.
11. As a user, I want to edit a Debt's counterparty name, date, or note at any time, without restriction.
12. As a user, I want a Debt's `direction` fixed for good once created, so a repayment against it is never ambiguous about which way money moves.
13. As a user, I want a `payable` Debt's amount to stay editable, so I can correct how much I owe.
14. As a user, I want a `receivable` Debt's amount locked once created, because it matches exactly one real Transaction that funded it. An edit could then disagree with what that Transaction recorded. To correct it, I delete the Debt and log it again.
15. As a user, I want to edit an existing repayment's amount, date, or note, with the edit applied directly to its Transaction, so I can correct a mistake.

### Deleting a Debt

16. As a user, I want to delete a Debt behind a typed confirmation, so I understand I'm about to remove a tracked record.
17. As a user, I want deleting a Debt to leave every linked Transaction in my Bank Account history by default, because that money moved. Then a bookkeeping cleanup never silently rewrites my Balance.
18. As a user, I want a clearly labeled option in the same confirmation to also delete the linked Transactions, so I can fully undo a real mistake, such as an accidental duplicate Debt, when I want the money record gone too.

### Forgiving a Debt

19. As a user, I want to mark a Debt as forgiven, writing off whatever is still outstanding no matter how much has been repaid, so I can close a debt I've decided not to collect or not to finish paying.
20. As a user, I want forgiving a Debt to use a plain yes/no confirmation, because it never touches real money or Transactions.
21. As a user, I want to un-forgive a Debt I forgave by mistake, reopening it without deleting and logging it again.
22. As a user, I want logging a new repayment against a forgiven Debt to reopen it, after a clear warning that this will happen, so a real payment isn't hidden by a "closed" status.
23. As a user, I want a Debt's status (Open, Settled or Forgiven) always computed live from its amount, its repayments, and whether it's forgiven, and never stored separately, so it can never drift from the data underneath.

### How Bank Account deletion affects Debts

24. As a user, when I delete a Bank Account that has a Transaction backing a Debt's repayment, I want that repayment to disappear, so the Debt's outstanding goes back up, without deleting the Debt itself.
25. As a user, when I delete a Bank Account that funded a `receivable` Debt, I want the Debt to stay with its origination link cleared instead of being deleted, so I don't lose repayments recorded against it on other accounts.
26. As a user, I want the Bank Account delete confirmation to warn me about every Debt it affects, whether a repayment is removed or a Debt loses its source, before I confirm, so a Debt that looks reopened or partly unexplained afterward doesn't surprise me.

### Ownership

27. As a user, I want every Debt view and action limited to my own Debts, never another user's, as everywhere else in this app.

## Implementation decisions

- **Modules touched.** A new `debts` module. The `transactions` schema is **not** changed. It gains no new column and knows nothing about Debts.
- **New table `debts`.** Its columns:
  - `id`.
  - `userId`, a foreign key to users with `ON DELETE CASCADE`.
  - `direction`, either `"payable"` or `"receivable"`, which can't change after creation.
  - `counterpartyName`, shipped as `name`. It is free-form text, with no dedicated entity.
  - `amount`, an integer in minor units.
  - `currency`, its own required column. Unlike Transaction and Allocation, a Debt never takes its currency from a Bank Account, because a `payable` has no Bank Account at creation.
  - `originatingTransactionId`, a nullable foreign key to `transactions.id` with `ON DELETE SET NULL`. Only a `receivable` can have it, set at creation when the user picks a source Bank Account. It is always `null` for a `payable`.
  - `note`, nullable text.
  - `date`, which the user can edit, defaulting to now.
  - `createdAt`.
  - `forgivenAt`, a nullable timestamp. It is the only piece of Debt state that can't be derived from other data. If it's set, the Debt is forgiven.
- **New table `debtPayments`, shipped as `repayments`.** Its columns:
  - `id`.
  - `debtId`, a foreign key to `debts.id` with `ON DELETE CASCADE`.
  - `amount`, `date` and `note`, all **nullable** and set **only when `transactionId` is null** (see the 2026-10-08 revision of story 4 below).
  - `transactionId`, a nullable, unique foreign key to `transactions.id`, so a Transaction backs at most one repayment. It has been `ON DELETE CASCADE` since 2026-10-21, and was `SET NULL` before that.
  - `createdAt`.

  A repayment stores its values in exactly one place, never both. Since 2026-10-21, the `repayments_one_storage_form` CHECK constraint enforces that. A repayment backed by a Transaction reads its amount, date and note through that join, following the same rule as Allocation having no currency of its own: no data is copied across a link. A repayment with no Transaction reads them from its own columns. Reading code goes through `toRepaymentEntry` in `src/modules/repayments/storage.server.ts`, which reads each form on its own terms.

- **`originatingTransactionId` and `debtPayments.transactionId` now behave differently on delete.** Both used to be `ON DELETE SET NULL`. Losing the linked Bank Account or Transaction was meant to clear only that link, never delete the parent row. For a Debt, the origination link clears and the Debt stays, as story 25 asks. `originatingTransactionId` still works that way. `transactionId` has cascaded since 2026-10-21, because a repayment backed by a Transaction has no values of its own, so clearing the link left a blank row (see the entry of that date). It also cascaded when first shipped, while a repayment's amount lived only on its Transaction. The 2026-10-08 revision below explains why it switched to `SET NULL` in between.
- **Direction sets the type of each Transaction.** The user doesn't choose it per record. Creating a `receivable` is an `expense`, because money leaves the source account, and a `receivable` repayment is `income`. A `payable` has no Transaction at creation, and a `payable` repayment is an `expense`.
- **Outstanding** is computed on read and never stored: `amount − Σ(debtPayments joined to transactions).amount`. It may go negative, because overpayment is allowed with no cap (see story 9). This follows the rule in `CONTEXT.md` that `Balance` and `Unallocated` are computed on read and never stored.
- **Status** is also computed and never stored. Check in this order: if `forgivenAt != null`, it's "Forgiven". Otherwise, if `outstanding ≤ 0`, it's "Settled". Otherwise it's "Open". Don't add a `status` column (see story 23). A stored status would silently go stale when a Bank Account deletion cascades away a repayment through code that has nothing to do with the Debt module.
- **Repayment validation.** Nothing caps a repayment against outstanding, because story 9 allows overpayment in both directions. The only rule that applies is the existing `Balance ≥ 0` check on every `expense` Transaction. It applies here only because a `payable` repayment happens to be an `expense`, not because of any Debt rule.
- **Editing.** `direction` is never editable. `receivable.amount` is never editable, so the user deletes the Debt and logs it again to correct it, following the rule that an Allocation can't be moved. `payable.amount` is editable. `counterpartyName`, `note` and `date` are editable in both directions. Editing a repayment backed by a Transaction edits that Transaction's amount, date and note directly, through the Transaction module's own edit path and validators, because the repayment holds no data of its own. A repayment with no Transaction (the 2026-10-08 revision of story 4) edits its own `amount`, `date` and `note` columns. A repayment's Bank Account, or its lack of one, can't be edited.
- **Forgiving.** Forgiving sets `forgivenAt = now`. It is all or nothing, with no partial write-off and no separate forgiven-amount field, behind a plain `confirm()`. Un-forgiving clears `forgivenAt`. Logging a new repayment against a forgiven Debt (`forgivenAt != null`) also clears `forgivenAt`, after a confirmation that warns the user it reopens the Debt.
- **Deleting.** Delete uses a typed confirmation, like Bank Account and Bucket (ADR 0001 and ADR 0002), not a plain `confirm()`. A Debt with repayments can be deleted, while Allocation and Transaction use a plain confirmation because deleting them loses no real history. By default, deleting removes only the `debts` row. Its `debtPayments` rows cascade away through `debtId`, and the linked `transactions` stay. A checkbox, unchecked by default and labeled "also delete the linked Transaction(s)", also deletes every Transaction the Debt links to: the origination, if there is one, and every repayment's Transaction. The code first looks up the linked Transaction ids, before the cascade on the `debts` row removes the `debtPayments` rows that hold them. It deletes those Transactions, then deletes the `debts` row. The copy must say plainly that checking the box changes money (see story 18), because the checkbox isn't cosmetic.
- **A required change in the `bank-accounts` module.** It is outside this spec's scope, but stories 24 to 26 need it. The existing typed confirmation for deleting a Bank Account (ADR 0001) must list the Debts it affects before the user confirms. For example: "Deleting Checking will also affect 1 Debt: Jane's ₱600 repayment will be undone, reopening 'Jane owes ₱1000' back to ₱600 outstanding." Without it, the cascades in stories 24 and 25 are correct but happen silently. This shipped on 2026-10-12 as a small change to the `bank-accounts` delete flow, with no separate spec (see Further notes).

## Out of scope

- **A dedicated Counterparty or Contact entity.** Only the free-text `counterpartyName`. A separate entity was rejected, following the app's habit of not modeling things until needed, as with Bucket and Goal. Revisit only if users ask for a person's history or a search across Debts.
- **Due dates, reminders or notifications.** The app has no email or push notifications anywhere, so a due date field would do nothing. Not designed here.
- **Partial forgiveness.** Forgiving is all or nothing by design (story 19). See Implementation decisions. A partial write-off would need its own append-only ledger, which is another table shaped like `debtPayments`. Not built.
- **Currency conversion.** A Debt's currency must match any Bank Account it moves money through (stories 2 and 5). The app has no conversion anywhere, and this spec adds none.
- **A Debt list or search across accounts.** This spec only designs a detail page per Debt, the same starting point Allocation had before `docs/specs/allocation-cross-account-and-bucket-list.md`. It could get the same treatment later.
- **How `Distribution` works with Debt**, such as splitting a logged income across Buckets _and_ Debts. It is a separate module, designed in [`distribution.md`](distribution.md). This spec makes the Debt side possible but doesn't design how they connect. See the `Distribution` entry in [`CONTEXT.md`](../../CONTEXT.md).
- **The change to the `bank-accounts` delete confirmation copy** described above. This spec's stories need it to avoid surprising users, but it changes another module's existing flow and isn't new Debt-module work.

## Further notes

- `CONTEXT.md` defines `Debt`. This spec assumes it instead of repeating it.
- `originatingTransactionId` can be null for a `receivable` even at creation, because picking a source Bank Account is optional (see stories 1 and 2). The original session said the source was mandatory and debited immediately, and that changed. It can also become `null` later, when deleting a Bank Account clears it (story 25). Don't add a database constraint such as `NOT NULL WHEN direction = 'receivable'`. It would break both the optional source at creation and the orphaning this spec chose over cascading the whole Debt.
- **Funding a `receivable` from several Bank Accounts at once was built, then reverted.** The original grilling session only considered one source account. A later implementation pass added a `debtOriginations` join table, with `debtId` and `transactionId` both `ON DELETE CASCADE`, so a receivable could be split across several accounts with an amount per account. It prototyped three split editors: a draggable proportional bar, percentage entry, and an auto-computed remainder. It worked, but splitting one loan across accounts turned out to be rare enough that the cost wasn't worth it, given the join table, the redistribution math and a multi-step editor. Before shipping, it was reverted to one optional `bankAccountId`, which is this spec's `originatingTransactionId`. If anyone revisits funding from several accounts, start from `debtOriginations` above, because that shape worked. In a join table, `ON DELETE CASCADE` on both foreign keys is correct, instead of the single foreign key's `SET NULL`. Losing one origination's account should drop only that one link, without orphaning or cascading the whole Debt.
- A grilling and domain-modeling session produced this whole spec, which was revised as stories 1 and 2 were built. Every decision above was worked through with concrete examples before it was locked in. The examples covered cleaning up duplicate entries, cascades from repayments across accounts, and how overpayment interacts with the existing `Balance` rules. None of it is a first guess.
- **2026-10-08 revision. A repayment's Bank Account became optional, reversing the original story 4, which made every repayment a real Transaction.** As first written, story 4 required every repayment to have a Bank Account. As first shipped, the `debtPayments` table had `transactionId NOT NULL UNIQUE` with `ON DELETE CASCADE`, and no `amount`, `date` or `note` of its own. A `receivable`'s creation was first drafted the same way, with a mandatory source debited right away, before story 1 made it optional (see the note above). Repayments were loosened the same way, for the same reason. A user should be able to record a repayment when the money moved outside this app, or when no real money moved at all, such as a `payable` written down by something other than a tracked account. So `repayments` gained its own nullable `amount`, `date` and `note` columns, filled only when there's no linked Transaction, never both (see Implementation decisions). `transactionId` became nullable with `ON DELETE SET NULL`, instead of `NOT NULL UNIQUE` with `CASCADE`. Implementation decisions was updated in place, so it no longer describes the shape from before the revision. `logRepaymentSchema.bankAccountId` is `z.string().nullable()`, not `.optional()`, because the form always sends the key, as an id string or an explicit `null`, and never leaves it out. What shipped before this revision still stands: logging a Debt (stories 1 to 3) and logging a repayment with a mandatory Bank Account (the original story 4, in commits `8b646b3`, `37ccc43`, `59db5cc` and `5d4abd2`). Only the part of story 4 that made a repayment's Bank Account mandatory changed.
- **2026-10-12. Editing a Debt shipped (stories 11 to 14).** The `debts` table first shipped with no `date` or `note` column. The ledger showed "Recorded" from the origination Transaction's date, or from `createdAt` when there was none. So story 11 needed both columns first, from migration `20261012125025_debt_date_and_note`. It is a plain generated migration, and `date` uses the same SQL default as `transactions.date`. That only worked because `debts` was empty in production when it shipped. SQLite rejects `ADD COLUMN` with a non-constant default such as `unixepoch()` on a table that already has rows. `debt.date` is the Debt's own value, and editing it does **not** change the origination Transaction's date. How editing works: `editDebtSchema` is a `strictObject` with no `direction` key, so it rejects any request that carries one (story 12). `amount` is optional, and `editDebt` throws if a request sends one for a `receivable` (story 14). The lock holds even for a receivable with no origination Transaction, because no source was picked or because story 25 orphaned it. That applies the "never editable" rule above literally, even though no Transaction could disagree in those cases. The UI is `EditDebtDialog` (`src/modules/debts/components/edit-debt-dialog.tsx`), opened from the debts table's row menu and from the detail page. For a receivable, it shows the direction read-only and the amount disabled, with a hint to delete the Debt and record it again.
- **2026-10-12. Recording a Debt also takes a `date` and an optional `note`.** Stories 1 and 3 only listed the amount, currency, counterparty name and source account, so `RecordDebtDialog` had no date or note inputs at first. Every Debt got the column default, now, and no note, which left story 11's edit as the only way to set them. `recordDebtSchema` now carries `date`, which the form defaults to today, and `note`, where an empty string is stored as `null`. For a `receivable` with a source account, the chosen date is also written to the origination Transaction, so the money leaves the account on the same day. The Transaction's note stays the generated `Loan to "<name>"`, separate from the Debt's note. After creation the two dates change independently, as the entry above says.
- **2026-10-12. Editing a repayment shipped (story 15).** Story 15 was written before the 2026-10-08 revision, so it only describes repayments backed by a Transaction. The shipped code handles both forms. `editRepayment` (`src/modules/repayments/functions.ts`) looks up the repayment by both `repaymentId` **and** `debtId`. `verifyUserDebtMiddleware` only proves the Debt belongs to the user, so without the `debtId` scope, any repayment id could be edited through a Debt the user owns. That is the same IDOR shape as the allocation and transaction fix. If the repayment has a Transaction, the edit goes to `editTransaction` with the Transaction's existing `type`, so its Balance check (`validateEditTransaction`) still applies. For example, it rejects raising a `payable` repayment past the account's unallocated balance, or lowering a `receivable` repayment below what's already allocated from it. Otherwise the repayment's own columns are updated. `editRepaymentSchema` is a `strictObject` with no `bankAccountId`, so a repayment can't move between accounts, or gain or lose an account. The user deletes it and logs it again once deletion exists. The UI is `EditRepaymentDialog`, opened from a row menu on each repayment in the detail page's ledger. The dialog names the linked account, so the user knows the edit changes that account's Transaction too.
- **2026-10-12. Deleting a Debt shipped (stories 16 to 18).** `deleteDebt` (`src/modules/debts/functions.ts`) takes `deleteDebtSchema`, a `strictObject` of `debtId` and a required `deleteTransactions` boolean. That boolean is story 18's checkbox, and the request always sends it. Unchecked, only the `debts` row is deleted, its `repayments` cascade, and every linked Transaction stays (story 17). Checked, the code first looks up the linked Transaction ids, meaning the origination and each repayment's Transaction, through `getDebtLinkedTransactionIds` in `src/modules/debts/utils.ts`, **before** deleting anything. Then one D1 `batch` deletes those Transactions and then the Debt, so the whole delete succeeds or fails together. Both foreign keys into `transactions` are `SET NULL`, so deleting the Transactions first is safe. The original design missed one case. Deleting a receivable's repayment, which is `income`, lowers that account's Balance and could push it below what's allocated from it. So `validateDeleteDebt` runs the same unallocated ≥ 0 check as `validateDeleteTransaction`, once per affected account with all of that account's linked Transactions removed together, and rejects the delete with the account's name. It runs both in the dialog (`onSubmitAsync`) and again inside `deleteDebt`. The UI is `DeleteDebtDialog` (`src/modules/debts/components/delete-debt-dialog.tsx`). It has a typed confirmation of the counterparty name, a repayment count, and a summary that changes with the checkbox (`DebtDeletionSummary`). Unchecked, the summary says the linked Transactions stay in their accounts, so no Balance changes. Checked, it shows each affected Bank Account's Balance before and after the delete. The checkbox only appears when the Debt has linked Transactions. The dialog only opens from the debts table's row menu, like Bank Account and Bucket, which offer Delete in their list menus but not on their detail pages. Deleting from the detail page would also flash "Debt not found", because the global invalidation refetches the page's query before the dialog can navigate away. A new `Checkbox` UI component (`src/components/ui/checkbox.tsx`, built on base-ui) was added for it.
- **2026-10-12. Forgiving a Debt shipped (stories 19 to 23).** It adds a nullable `debts.forgiven_at` column, from migration `20261012140456_debt_forgiven_at`. Forgive and Unforgive are row-menu items in `DebtActionsDropdownMenu`, behind the plain yes/no `confirm()` of story 20, not a dedicated dialog or button, so the detail page has no Forgive control. Only one of the two shows, depending on status: Forgive when Open, Unforgive when Forgiven, and neither for a Settled Debt. `forgiveDebt` rejects a Debt that is already forgiven or settled, because there would be nothing to write off. `unforgiveDebt` only clears `forgivenAt`. Neither touches Transactions or balances. For story 22, `logRepayment` clears `forgivenAt` in the same D1 `batch` as the repayment insert, with or without a Bank Account, and `LogRepaymentDialog` first asks for a "Log & Reopen" confirmation when the Debt is forgiven. For story 23, `getDebtStatus` (`src/modules/debts/utils.ts`) computes `forgiven`, `settled` or `open` on read, in that order, from `forgivenAt`, `amount` and the repayments. It feeds a Status column in the debts table and a `DebtStatusBadge` beside the detail page's heading. Forgiving doesn't change Outstanding, so a forgiven Debt still shows what was left when it was written off.
- **2026-10-12. Two gaps closed after a spec audit.**
  1. Recording a `receivable` with a source account never checked that the account could cover the loan. The picker only hides accounts with zero unallocated, so any larger amount pushed the account's unallocated balance negative. That broke the `Balance ≥ 0` rule every other `expense` path enforces. `validateDebtSourceBankAccount` now takes `amount` and runs the same unallocated check as `validateLogTransaction`, both from `RecordDebtDialog`'s `onSubmitAsync` and inside `recordDebt`.
  2. `DebtLedgerTable` derived its own Open or Settled badge from outstanding, so the ledger said "Open" for a forgiven Debt while the heading said "Forgiven" (story 23). It now renders `DebtStatusBadge` from `getDebtStatus`. The heading's duplicate badge was dropped, so the ledger's badge is the only status badge on the detail page.
- **2026-10-12. How Bank Account deletion affects Debts shipped (stories 24 to 26).** Story 25 needed no new code. Deleting a Bank Account cascades to its Transactions, and the `SET NULL` on `debts.originatingTransactionId` orphans the Debt. Story 24 needed code. Since the 2026-10-08 revision, `repayments.transactionId` was also `SET NULL`, so the cascade left the repayment row behind with no Transaction and no `amount`, `date` or `note` of its own. That showed as a blank, zero-amount row in the ledger. It added nothing to outstanding, so the number was right, but the repayment hadn't disappeared as story 24 asks. `deleteBankAccount` (`src/modules/bank-accounts/functions.ts`) now deletes every repayment whose Transaction belongs to the account, in the same D1 `batch` as the account. Repayments with no Bank Account, or made through other accounts, stay. No Balance check is needed, because the only Transactions removed are the deleted account's own. For story 26, `getBankAccountLinkedDebts` (`src/modules/debts/functions.ts`) returns the user's Debts funded from or repaid through the account. `DeleteBankAccountDialog` fetches it with the account and renders `BankAccountDeletionDebtsItem` (`src/modules/debts/components/bank-account-deletion-debts-item.tsx`) as one more bullet in its list of consequences. For each Debt, it gives the count and total of the repayments removed, the outstanding before and after, any status change such as Settled to Open, and, if the account funded the Debt, that the Debt stays with no source account. Deleting a single Transaction that backs a repayment, from the transactions list, still leaves the same blank row. That is story 24's problem through a different path, and this change doesn't fix it.
- **2026-10-12. Two record-dialog gaps closed after drafting test cases.**
  1. `recordDebtSchema` and `editDebtSchema` accepted `amount: 0` because of `min(0)`, so a user could log a 0.00 Debt that was Settled on creation. Both now require at least 0.01, with the same rule and message as the repayment schemas, and the amount inputs' `min` matches.
  2. Changing `RecordDebtDialog`'s currency now clears the picked source account. The picker only lists accounts in the selected currency, so the old pick would be a stale account in the wrong currency that only failed on submit.
- **2026-10-13. The detail page's note moved into the ledger.** Story 10 lists the note on the detail page, but it was a loose paragraph between the heading and the ledger. It now renders as a quote beside the opening entry, "Lent to X" or "Borrowed from X", in `DebtLedgerTable`, because it describes how the Debt began. This was chosen over a heading popover and a side card.

- **2026-10-27. The Debts list's Last Repayment Date and Ledger Movement columns became one Activity column.** Stories 8, 10 and 23 are unchanged. The Last Repayment Date badge said "No Repayments" for a Debt with none, however old it was, and Ledger Movement's step chart only repeated the ring's progress, with steps spaced by repayment instead of by date. Neither could tell the User which Debts had gone quiet. `DebtActivityCell` (`debt-activity-cell.tsx`) replaces both. Its first line is "Last repaid <relative date>", or "No repayments yet", and its second is "Recorded <relative date>" plus " · N repayments" when there are any. A date within the last day reads "today" instead of "now", and each date's tooltip shows the full date. The column sorts by the Debt's last activity, which is its last repayment date and falls back to the date it was recorded when there is no repayment, so a Debt with none sorts by its age. Settled and Forgiven Debts show the same cell. `DebtBalanceSparkline` is deleted. Its variants are on the `prototype/debts-index` branch (variant C). The stale flag was not built, because its threshold isn't something the data defines.
