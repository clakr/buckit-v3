# Spec: Debt Module

No issue tracker is used for this project. This file is the actionable checklist — its `status: ready-for-agent` frontmatter stands in for the triage label a tracker would normally carry. Update the status (e.g. `in-progress`, `done`) as work proceeds.

## Problem Statement

`Debt` is a placeholder entity noted in `CONTEXT.md` but not yet implemented at all — no schema, no module, no UI. There is currently no way to track money owed to or by another person. A Bank Account's Balance can never go negative (it models liquid assets only), so credit/liability/IOU tracking has nowhere to live today.

## Solution

A `Debt` module tracking money owed in either direction (`receivable`/`payable`), with an asymmetric relationship to Bank Account: a `receivable`'s creation can optionally be a real money-movement event (funds leave a chosen Bank Account immediately) if a source account is picked — picking one is optional, so a receivable can also be recorded with no Bank Account at all; a `payable`'s creation is always a pure record with no Bank Account involved until repayment. Repayments — many, partial, over time, either direction — follow the same optional-Bank-Account pattern: picking one records the repayment as a real `Transaction` row too; leaving it empty keeps the repayment a pure record against the Debt only. Either way the repayment is kept linked to its Debt via a dedicated `debtPayments` table rather than teaching `transactions` about Debt. A Debt can also be manually forgiven (an all-or-nothing, reversible write-off).

This spec was produced by a grilling/domain-modeling session, then partially built and refined afterward — creating a Debt (stories 1–3), logging repayments (stories 4–9), viewing a Debt (story 10), editing a Debt (stories 11–14), editing a repayment (story 15), and deleting a Debt (stories 16–18), forgiving a Debt (stories 19–23), and Bank Account deletion interplay (stories 24–26) are implemented; the ownership audit (story 27) is still design-only. See the Further Notes for what changed between the original session and what shipped.

## User Stories

### Logging a Debt

1. As a user, I want to log a new Debt where someone owes me money (`receivable`), giving an amount, a currency, a free-text counterparty name, and optionally a single source Bank Account, so that if I do pick one, the money leaving that account to fund the loan is recorded as a real Transaction — and if I don't, the Debt is still recorded (e.g. cash lent, or money that moved outside this app).
2. As a user, I want the Bank Account picker when logging a `receivable` Debt to only show accounts whose currency matches the currency I've picked for the Debt, and to only show accounts with unallocated balance available, so I can't accidentally fund it from a mismatched-currency or fully-committed account (this app has no FX conversion anywhere).
3. As a user, I want to log a new Debt where I owe someone money (`payable`), with just an amount, currency, and counterparty name — no Bank Account required — so I can record an obligation that didn't originate through money already tracked in this app (a cash loan, a pre-existing debt, a promise).

### Repaying a Debt

4. As a user, I want to log a repayment against any Debt, regardless of direction, giving an amount, date, optional note, and optionally a Bank Account, so that if I do pick one, the money genuinely moving is recorded as a real Transaction tied back to that Debt — and if I don't, the repayment is still recorded as a pure reduction of what's outstanding (e.g. cash repaid, or money that moved outside this app), same reasoning as a `payable`'s bank-account-less creation (story 3).
5. As a user, I want the Bank Account picker for a repayment to only show accounts matching the Debt's currency, same reasoning as story 2.
6. As a user, I want repayments to be freely made from any matching-currency Bank Account, not constrained to the account a `receivable` was originally funded from, so real-world flexibility (lent from Checking, repaid into Savings) is supported.
7. As a user, I want to log multiple partial repayments against a single Debt over time, so I can track it being paid down gradually rather than all at once.
8. As a user, I want a Debt's outstanding amount to be computed live from its original amount minus everything repaid against it, so I never trust a number that could go stale.
9. As a user, I want to be able to log a repayment larger than what's currently outstanding, so an overpayment (accidental or deliberate) isn't blocked — the app shouldn't assume it's always a mistake.

### Viewing and editing

10. As a user, I want to see a Debt's counterparty name, direction, amount, live outstanding, currency, date, and note on its detail page, along with every repayment logged against it, so I have a full picture in one place.
11. As a user, I want to edit a Debt's counterparty name, date, or note at any time, without restriction.
12. As a user, I want a Debt's `direction` to be permanently fixed once created, so a repayment logged against it is never ambiguous about which way money should move.
13. As a user, I want a `payable` Debt's amount to stay freely editable, so I can correct how much I actually owe.
14. As a user, I want a `receivable` Debt's amount to be locked once created — it's tied 1:1 to the real Transaction that funded it — so an edit can't desync from what that Transaction actually recorded; to correct it, I delete and re-log instead.
15. As a user, I want to edit an existing repayment's amount, date, or note, with the edit applying directly to its underlying Transaction, so I can correct a mistake.

### Deleting a Debt

16. As a user, I want to delete a Debt behind a typed confirmation, so I understand I'm about to remove a tracked record.
17. As a user, I want deleting a Debt to, by default, leave every Transaction it's linked to untouched in my Bank Account history — that money genuinely moved — so my Balance is never silently rewritten by a bookkeeping cleanup.
18. As a user, I want an explicit, clearly-labeled option in that same confirmation to also delete the linked Transaction(s), so I can fully undo a genuine mistake (e.g. an accidental duplicate Debt) when I actually want the real money record gone too.

### Forgiving a Debt

19. As a user, I want to manually mark a Debt as forgiven, writing off whatever is still outstanding regardless of how much has actually been repaid, so I can close out a debt I've decided not to collect or pay the rest of.
20. As a user, I want forgiving a Debt to use a simple yes/no confirmation, since it never touches real money or Transactions.
21. As a user, I want to manually un-forgive a Debt I forgave by mistake, reopening it without deleting and re-logging.
22. As a user, I want logging a new repayment against an already-forgiven Debt to automatically reopen it — after a clear warning that this is about to happen — so a genuine payment isn't silently swallowed by a "closed" status.
23. As a user, I want a Debt's displayed status (Open / Settled / Forgiven) to always be computed live from its amount, its repayments, and whether it's been forgiven — never a separately stored value — so it can never drift out of sync with the data underneath it.

### Interaction with Bank Account deletion

24. As a user, when I delete a Bank Account that has a Transaction linked to a Debt as a repayment, I want that specific repayment link to disappear (the Debt's outstanding goes back up accordingly) without destroying the Debt itself.
25. As a user, when I delete a Bank Account that funded a `receivable` Debt's origination, I want that Debt to survive with its origination link cleared (orphaned) rather than being deleted outright, so I don't silently lose repayment history recorded against it on other, untouched accounts.
26. As a user, I want the Bank Account delete confirmation to warn me about any Debts that will be affected (a repayment link removed, or an origination orphaned) before I confirm, so I'm not surprised afterward by a Debt that looks reopened or partially unexplained.

### Ownership

27. As a user, I want every Debt view/action scoped to my own Debts only, never another user's — same boundary already enforced everywhere else in this app.

## Implementation Decisions

- **Modules touched**: new `debts` module. `transactions` schema is **not** modified — no new column, no awareness of Debt added to it.
- **New table `debts`**: `id`, `userId` (FK → users), `direction` (`"payable" | "receivable"`, immutable after creation), `counterpartyName` (text, free-form — no dedicated entity), `amount` (integer, minor units), `currency` (own column, always required — unlike Transaction/Allocation, never inherited, since `payable` has no Bank Account at creation), `originatingTransactionId` (nullable FK → `transactions.id`, `ON DELETE SET NULL`; optionally set at creation for `receivable` only if a source Bank Account was picked, always `null` for `payable`), `note` (nullable text), `date` (user-editable, defaults to now), `createdAt`, `forgivenAt` (nullable timestamp — the only genuinely non-derivable piece of Debt state; presence means forgiven).
- **New table `debtPayments`** (shipped as `repayments`): `id`, `debtId` (FK → `debts.id`, `ON DELETE CASCADE`), `amount`, `date`, `note` — all three **nullable**, set **only when `transactionId` is null** (see story 4's 2026-10 revision below); `transactionId` (nullable FK → `transactions.id`, `ON DELETE SET NULL`, unique — a Transaction backs at most one repayment), `createdAt`. Whichever is present is the single source of truth — never both: a repayment backed by a Transaction reads amount/date/note via that join (same "no data duplicated across the link" principle as Allocation having no currency of its own); a repayment with no Transaction reads them off its own columns instead. Reading code must resolve through the Transaction first, falling back to the row's own columns — see `getRepaymentAmount`/`getRepaymentDate` in `src/modules/repayments/utils.ts`.
- **`originatingTransactionId` vs. `debtPayments.transactionId` — same `ON DELETE SET NULL` behavior now, for the same reason.** Both deliberately avoid cascading away the parent row: losing the linked Bank Account/Transaction should only clear that one link (outstanding recomputes upward for a repayment; the origination becomes orphaned for a Debt) — see stories 24–26 and the worked example this reasoning came from, in session notes. (Originally `debtPayments.transactionId` cascaded the repayment row itself, back when a repayment's amount lived only on its Transaction — see the 2026-10 revision note below for why that changed.)
- **Direction → cash-flow mapping** (fixed, not user-chosen per record): `receivable` creation = `expense` (money leaving the source account); `receivable` repayment = `income`. `payable` has no creation-time Transaction; `payable` repayment = `expense`.
- **Outstanding**, computed on read, never stored: `amount − Σ(debtPayments joined to transactions).amount`. Allowed to go negative (overpayment permitted, no cap — see story 9). This mirrors `Balance`/`Unallocated`'s existing "computed on read, never stored" precedent in `CONTEXT.md`.
- **Status**, also computed, never stored, in priority order: `forgivenAt != null → "Forgiven"`; else `outstanding ≤ 0 → "Settled"`; else `"Open"`. Do not add a `status` column — see story 23; a stored status is exactly the kind of value that would silently go stale when a Bank Account deletion cascades away a repayment out from under a Debt through a code path unrelated to the Debt module.
- **Repayment validation**: no cap against outstanding (story 9 — overpayment allowed for both directions). The only invariant still in play is the existing, unrelated `Balance ≥ 0` check already enforced on every `expense` Transaction (applies here only because a `payable` repayment happens to be an `expense`, not because of any Debt-specific rule).
- **Editing**: `direction` never editable. `receivable.amount` never editable (delete + re-log to correct — same precedent as Allocation's non-reassignment). `payable.amount` freely editable. `counterpartyName`/`note`/`date` freely editable, both directions. Editing a repayment edits its linked `Transaction` directly (amount/date/note) — reuses the Transaction module's own edit path/validators, since a Transaction-backed repayment holds no data of its own to edit; a repayment with no Transaction (story 4's 2026-10 revision) edits its own `amount`/`date`/`note` columns instead. A repayment's Bank Account (or lack of one) is not editable.
- **Forgiving**: sets `forgivenAt = now`. All-or-nothing (no partial write-off, no separate forgiven-amount field). Plain `confirm()`. Un-forgiving (manual) clears `forgivenAt`. Logging a new repayment against a forgiven Debt (`forgivenAt != null`) also clears `forgivenAt` as a side effect, gated by a confirmation alert warning the user this reopens it.
- **Delete**: typed confirmation (Bank Account/Bucket style, per ADR 0001/0002 precedent), not plain `confirm()` — chosen specifically because a Debt with repayments can be deleted, unlike Allocation/Transaction's plain-confirm precedent which assumes no meaningful history is lost. Default: delete the `debts` row only (cascades away its `debtPayments` rows via `debtId`; linked `transactions` are untouched). Checkbox option ("also delete the linked Transaction(s)"), unchecked by default: additionally deletes every Transaction the Debt links to (the origination, if any, plus every repayment's Transaction) — implemented by resolving the linked Transaction ids first (before the `debts` row's `debtPayments` cascade removes that linking info), deleting those Transactions, then deleting the `debts` row itself. Copy must make the money-affecting consequence of checking the box explicit (see story 18) — this is not a cosmetic checkbox.
- **Follow-up on `bank-accounts` module (not this spec's scope, but required for stories 24–26 to be true in practice)**: the existing typed-confirmation copy for deleting a Bank Account (ADR 0001) needs to be extended to enumerate affected Debts before the user confirms — e.g. "Deleting Checking will also affect 1 Debt: Jane's ₱600 repayment will be undone, reopening 'Jane owes ₱1000' back to ₱600 outstanding." Without this, stories 24/25's cascade behavior is technically correct but silent/surprising. Flag this as a small required change to `bank-accounts`' delete flow when this module is built, not a separate spec.

## Testing Decisions

Deferred, for the same reason already recorded in `docs/specs/bank-account-crud.md`, `docs/specs/bucket-crud.md`, `docs/specs/transaction-list-and-transfer.md`, and `docs/specs/allocation-cross-account-and-bucket-list.md`: no test harness exists yet anywhere in this repo. Once one exists, the highest-value cases to cover first: the outstanding/status computation (especially the "overpaid" and "forgiven-then-reopened" branches), the `originatingTransactionId`/`debtPayments.transactionId` orphaning on Bank Account deletion (stories 24–25), and the checkbox delete path's transaction-then-debt deletion ordering.

## Out of Scope

- **A dedicated Counterparty/Contact entity.** Free-text `counterpartyName` only — explicitly rejected in favor of the app's minimalism precedent (Bucket/Goal left undesigned until needed). Revisit only if per-person history/search across Debts becomes a real ask.
- **Due dates, reminders, or any notification concept.** No notification infrastructure (email/push) exists anywhere in this app — a due date field would be inert. Not designed here.
- **Partial forgiveness.** Forgiving is all-or-nothing by design (story 19) — see the reasoning in the Implementation Decisions section. A partial write-off would need its own append-only ledger, structurally another `debtPayments`-shaped table; not built.
- **FX conversion.** A Debt's currency must match any Bank Account it transacts with (stories 2, 5) — there is no conversion mechanism anywhere in this app, and none is introduced here.
- **A standalone, cross-account Debt list/search view.** Only a per-Debt detail page is designed here, same starting point Allocation had before `docs/specs/allocation-cross-account-and-bucket-list.md`. Could get the same treatment later.
- **`Distribution`'s integration with Debt** (splitting a logged income across Buckets _and_ Debts) — still a separate, undesigned module; this spec unblocks its Debt half but doesn't design the integration itself. See the `Distribution` entry in [`CONTEXT.md`](../../CONTEXT.md).
- **The `bank-accounts` delete-confirmation copy change** noted above — required for this spec's stories to be non-surprising in practice, but is a change to a different module's existing flow, not new Debt-module work.

## Further Notes

- Resolved vocabulary for `Debt` lives in `CONTEXT.md`. This spec assumes it as context rather than repeating it.
- `originatingTransactionId` is never guaranteed non-null for a `receivable`, even at creation time — picking a source Bank Account is optional (see stories 1–2 above, changed from the original session's "mandatory-and-immediate" framing). It can also become `null` later via Bank Account deletion (story 25) when it _was_ set. Don't enforce a `NOT NULL WHEN direction = 'receivable'` constraint at the DB level; that would break both the optional-at-creation case and the orphaning behavior this spec deliberately chose over cascading the whole Debt.
- **Funding a `receivable` from multiple Bank Accounts at once was built, then reverted.** After the original grilling session (which only ever considered a single source account), an implementation pass added a `debtOriginations` join table (`debtId`, `transactionId`, both `ON DELETE CASCADE`) so a receivable could be split across several accounts with per-account amounts — three different split-editor UIs were prototyped (a draggable proportional bar, percentage entry, auto-computed remainder). The mechanism worked, but splitting one loan across several accounts turned out to be a rare enough case that the complexity — a join table, redistribution math, a multi-step editor — wasn't worth it. Reverted to a single, optional `bankAccountId` (this spec's `originatingTransactionId`) before shipping. If multi-account funding is revisited, don't re-derive the join-table design from scratch — `debtOriginations` above is the shape that worked; the `ON DELETE CASCADE` on both FKs (rather than the single FK's `SET NULL`) is correct for a join table since losing one origination's account should only drop that one link, not orphan-or-cascade the whole Debt.
- This entire spec is the output of a grilling/domain-modeling session, revised afterward as stories 1–2 were actually built — every decision above was explicitly worked through with concrete worked examples (duplicate-entry cleanup, cross-account repayment cascades, overpayment interaction with `Balance`'s existing invariants) before being locked in. Nothing here is a first-pass guess.
- **2026-10-08 revision — a repayment's Bank Account became optional, reversing story 4's original "always a real Transaction" framing.** Story 4 as originally written (and the `debtPayments`/`transactions` join as originally shipped — `transactionId NOT NULL UNIQUE`, `ON DELETE CASCADE`, no `amount`/`date`/`note` of its own) required every repayment to carry a Bank Account, mirroring how a `receivable`'s creation was first drafted "mandatory-and-immediate" before story 1 loosened it (see the note above). The same loosening was applied to repayments for the same reason: a repayment should be recordable even when the money moved outside this app, or isn't a real movement at all (e.g. a `payable` being written down by something other than a tracked account). This required `repayments` to gain its own nullable `amount`/`date`/`note` columns, populated only when there's no linked Transaction (never both — see the Implementation Decisions entry above), and `transactionId` to become nullable with `ON DELETE SET NULL` instead of `NOT NULL UNIQUE ... CASCADE` — see the Implementation Decisions entries above, now updated in place rather than left to describe the pre-revision shape. `logRepaymentSchema.bankAccountId` is `z.string().nullable()`, not `.optional()` — the form always submits the key, as an id string or explicit `null`, never omits it. Recap of what was already shipped before this revision: logging a Debt (stories 1–3) and logging a repayment with a mandatory Bank Account (story 4's original form, commits `8b646b3`/`37ccc43`/`59db5cc`/`5d4abd2`) — both still stand; only the "Bank Account is mandatory for a repayment" half of story 4 changed.
- **2026-10-12 — editing a Debt (stories 11–14) shipped.** The `debts` table as first shipped had no `date` or `note` column at all (the ledger showed "Recorded" from the origination Transaction's date, falling back to `createdAt`), so story 11 needed both added first (migration `20261012125025_debt_date_and_note`). It's a plain generated migration; `date` uses the same SQL default as `transactions.date`. That only works because `debts` was empty in prod when it shipped: SQLite rejects `ADD COLUMN` with a non-constant default like `unixepoch()` on a table that already has rows. `debt.date` is the Debt's own value; editing it does **not** touch the origination Transaction's date. Edit mechanics: `editDebtSchema` is a `strictObject` with no `direction` key (story 12 — a request carrying one is rejected outright); `amount` is optional, and `editDebt` throws if one is sent for a `receivable` (story 14). That lock holds even for a receivable with no origination Transaction (no source account picked, or orphaned by story 25), applying the "never editable" rule above literally even though there's no Transaction to desync from in those cases. The UI is `EditDebtDialog` (`src/modules/debts/components/edit-debt-dialog.tsx`), opened from the debts table row menu and from the detail page; it shows direction read-only and the amount disabled, with a "delete and record it again" hint, for receivables.
- **2026-10-12 — recording a Debt now takes a `date` and optional `note` too.** Stories 1 and 3 only listed amount, currency, counterparty name (and the source account), so `RecordDebtDialog` originally had no date/note inputs and every Debt got the column default (now) and no note — leaving story 11's edit as the only way to set them. `recordDebtSchema` now carries `date` (form defaults to today) and `note` (empty string stored as `null`). For a `receivable` with a source account, the chosen date is also written to the origination Transaction, so the money leaving the account lands on the same day; the Transaction's note stays the generated `Loan to "<name>"`, and the Debt's note is kept separate. After creation the two dates are independent, per the entry above.
- **2026-10-12 — editing a repayment (story 15) shipped.** Story 15 predates the 2026-10-08 revision, so it only describes the Transaction-backed case; both are handled. `editRepayment` (`src/modules/repayments/functions.ts`) looks the repayment up by `repaymentId` **and** `debtId` — `verifyUserDebtMiddleware` only proves the Debt is the user's, so without the `debtId` scope any repayment id could be edited through an owned Debt (same IDOR shape as the allocation/transaction fix). If it has a Transaction, the edit is forwarded to `editTransaction` with the Transaction's existing `type`, so its Balance check (`validateEditTransaction`) still applies — e.g. raising a `payable` repayment past the account's unallocated balance, or lowering a `receivable` one below what's already been allocated from it, is rejected; otherwise the repayment's own columns are updated. `editRepaymentSchema` is a `strictObject` with no `bankAccountId`: moving a repayment between accounts, or attaching/detaching one, isn't supported — delete and re-log once deletion exists. The UI is `EditRepaymentDialog`, opened from a row menu on each repayment in the detail page's ledger; the dialog names the linked account so it's clear the edit changes that account's Transaction too.
- **2026-10-12 — deleting a Debt (stories 16–18) shipped.** `deleteDebt` (`src/modules/debts/functions.ts`) takes `deleteDebtSchema` — a `strictObject` of `debtId` plus a required `deleteTransactions` boolean (story 18's checkbox, never omitted). Unchecked, only the `debts` row is deleted; its `repayments` cascade, and every linked Transaction stays (story 17). Checked, the linked Transaction ids (origination plus each repayment's, via `getDebtLinkedTransactionIds` in `src/modules/debts/utils.ts`) are resolved **before** anything is deleted, then one D1 `batch` deletes those Transactions and then the Debt, so it's all-or-nothing. Both FKs into `transactions` are `SET NULL`, so the Transaction-first order is safe. The original design didn't anticipate one thing: deleting a receivable's repayment (an `income`) lowers that account's Balance and could push it below what's allocated from it. So `validateDeleteDebt` runs the same unallocated-≥-0 check `validateDeleteTransaction` does, once per affected account with all its linked Transactions removed together, and rejects the delete naming the account. It runs both in the dialog (`onSubmitAsync`) and again inside `deleteDebt`. The UI is `DeleteDebtDialog` (`src/modules/debts/components/delete-debt-dialog.tsx`): typed confirmation against the counterparty name, a repayment count, and a line that changes with the checkbox, between "linked transactions stay in your account history — no balance changes" and a destructive-coloured "will be permanently deleted from "<accounts>", changing their balances". The checkbox only appears when the Debt has linked Transactions. It's opened from the debts table row menu only, following Bank Account/Bucket, which offer Delete from their list menus but not their detail pages. Deleting from the detail page would also briefly show "Debt not found", because the global invalidation refetches the page's query before the dialog could navigate away. A new `Checkbox` UI primitive (`src/components/ui/checkbox.tsx`, base-ui) was added for it.
- **2026-10-12 — forgiving a Debt (stories 19–23) shipped.** New nullable `debts.forgiven_at` (migration `20261012140456_debt_forgiven_at`). Forgive and Unforgive are row-menu items (`DebtActionsDropdownMenu`) behind the plain yes/no `confirm()` of story 20, rather than a dedicated dialog or button, so no Forgive control exists on the detail page. Only one of the two shows, by status: Forgive when Open, Unforgive when Forgiven. Neither shows for a Settled Debt. `forgiveDebt` rejects an already-forgiven or settled Debt, since there'd be nothing to write off. `unforgiveDebt` just clears `forgivenAt`. Neither touches Transactions or balances. Story 22: `logRepayment` clears `forgivenAt` in the same D1 `batch` as the repayment insert (both with and without a Bank Account), and `LogRepaymentDialog` asks for a "Log & Reopen" confirmation first when the Debt is forgiven. Story 23: `getDebtStatus` (`src/modules/debts/utils.ts`) computes `forgiven | settled | open` on read, in that priority, from `forgivenAt`, `amount` and the repayments. It feeds a Status column in the debts table and a badge beside the detail page's heading (`DebtStatusBadge`). Outstanding itself is unchanged by forgiveness, so a forgiven Debt still shows what was left when it was written off.
- **2026-10-12 — two gaps closed after a spec audit.** (1) Recording a `receivable` with a source account never checked that the account could cover the loan: the picker only hides accounts with zero unallocated, so any larger amount pushed the account's unallocated balance negative, breaking the `Balance ≥ 0` invariant every other `expense` path enforces. `validateDebtSourceBankAccount` now takes `amount` and runs the same unallocated check as `validateLogTransaction`, both from `RecordDebtDialog`'s `onSubmitAsync` and inside `recordDebt`. (2) `DebtLedgerTable` derived its own Open/Settled badge from outstanding, so a forgiven Debt read "Open" there while the heading said "Forgiven" (story 23). It now renders `DebtStatusBadge` from `getDebtStatus`, and the heading's duplicate badge was dropped, leaving the ledger's as the detail page's only status badge.
- **2026-10-12 — Bank Account deletion interplay (stories 24–26) shipped.** Story 25 needed no new code: deleting a Bank Account cascades its Transactions, and `debts.originatingTransactionId`'s `SET NULL` orphans the Debt. Story 24 did. Since the 2026-10-08 revision, `repayments.transactionId` is also `SET NULL`, so the cascade left the repayment row behind with no Transaction and no `amount`/`date`/`note` of its own: a blank, zero-amount row in the ledger. It also contributed nothing to outstanding, so the number was right, but the link hadn't "disappeared" as story 24 asks. `deleteBankAccount` (`src/modules/bank-accounts/functions.ts`) now deletes every repayment whose Transaction belongs to the account, in the same D1 `batch` as the account itself. Repayments with no Bank Account, or through other accounts, are untouched. No Balance check is needed: the only Transactions removed are the deleted account's own. Story 26: `getBankAccountLinkedDebts` (`src/modules/debts/functions.ts`) returns the user's Debts funded from or repaid through the account. `DeleteBankAccountDialog` fetches it alongside the account and renders `BankAccountDeletionDebtsItem` (`src/modules/debts/components/bank-account-deletion-debts-item.tsx`) as one more bullet in its consequences list. Per Debt it gives the count and total of repayments removed, the outstanding before and after, any status change (e.g. Settled to Open), and, if the account funded it, that the Debt stays with no source account. Deleting a single Transaction that backs a repayment (from the transactions list) still leaves the same blank row behind. That's the same shape as story 24 through a different path, and isn't fixed here.
- **2026-10-12 — two record-dialog gaps closed after test-case drafting.** (1) `recordDebtSchema` and `editDebtSchema` accepted `amount: 0` (`min(0)`), so a 0.00 Debt could be logged and was Settled on creation. Both now require at least 0.01, same rule and message as the repayment schemas; the amount inputs' `min` follows. (2) Changing `RecordDebtDialog`'s currency now clears the picked source account, since the picker only lists accounts in the selected currency and the old pick would otherwise be a stale, mismatched value that only failed on submit.
- **2026-10-13 — the detail page's note moved into the ledger.** Story 10 lists the note on the detail page, but it was a loose paragraph between the heading and the ledger. It now renders as a quote beside the opening entry ("Lent to X" / "Borrowed from X") in `DebtLedgerTable`, since it describes how the Debt began. Chosen over a heading popover and a side card.
- **2026-10-13 — story 26's warning moved into a before → after table.** `BankAccountDeletionDebtsItem` is gone. `DeleteBankAccountDialog` now renders `BankAccountDeletionSummary` (`src/modules/bank-accounts/components/bank-account-deletion-summary.tsx`): one sentence for what's deleted with the account (its transactions, allocations and debt repayments), then a "Changes elsewhere" table with a Before and After column. Each affected Debt is a row with its outstanding before and after, a status badge on both sides when the status changes, and "loses its source account" when the account funded it. Story 26's content is unchanged; only the layout is. Chosen by prototype (branch `prototype/delete-bank-account-affected-data`, variant F) over a two-box split, a side-by-side layout and a cascade stepper. The same table also lists each affected Bucket's balance before and after, so the dialog now fetches every bucket too.
